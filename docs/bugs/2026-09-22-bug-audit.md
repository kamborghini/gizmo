# Bug audit, 2026-09-22

Second whole-app audit of Reactor (repo gizmo), run against `cba9d24` on `main`, the commit that closed every row of [the 2026-09-19 register](2026-09-19-bug-audit.md). Written in report mode; Cameron then asked for the P2s and the P3s to be fixed, and all 48 are (section 9). The two hypotheses and the area this audit could not cover are still open.

## Executive summary

**48 confirmed bugs: 0 P0, 0 P1, 13 P2, 35 P3**, plus 2 hypotheses that depend on undocumented World Options behaviour. 43 were reproduced by running the real code, and 5 are unambiguous on reading. Every finder's proof script was re-run by the main session and gave the same output.

**One area is not covered.** The access, identity and AI-boundary review (the role and tab matrix, sessions and sign-in, the four doors, the AI tool layer and prompt injection) could not be completed in this session: the finder's report and the main session's own review of it were both stopped by a safety classifier. It needs its own pass. Three items the other finders raised in that territory (`mailfin-07`, `mailfin-13`, `spa-03` in the working files) are held for it, and the items left open by the 2026-09-08 security pass are still open.

**No P0 or P1.** Nothing found destroys data outright or takes the app down. The weight is in P2s where the app quietly does the wrong thing with money, mail or records:

- **A1** Saving the Team tab picker for an account on the default tabs grants it Xero sync
- **A2** Undo on the print toast of a made order's reprint tags it Unprocessed, and Ready to make then puts the made order back into To make
- **A3** Reconciliation never looks at a finance-mailbox thread again once walked: a new invoice or remittance on that conversation is never read
- **A4** A scanned invoice read on a night the AI call fails is stored as 'ignored' and its thread marked seen, so it is never read again
- **A5** When Xero cannot be read, the sweep checks new Shopify orders against the Xero copy cached by the last good sweep and reports each as a sale missing from Xero
- **A6** A remittance's payment is 'found' by amount alone: a deleted payment, a payment to a supplier, or one another remittance already used all hide the missing receipt
- **A7** customers/redact leaves the person's deals, leads and website-enquiry thread behind, with their name, message and phone number
- **A8** A second Pipedrive import on the same day overwrites the snapshot taken before the first
- **A9** A gateway 5xx on a courier booking is reported as a plain failure, the Book button re-arms, and a second press books and charges again
- **A10** Attachments sent from Gmail or Apple Mail are dropped: the Inbox shows no file to save, and reconciliation never reads the supplier's PDF
- **A11** An inbox filter that gives an email to someone and takes it out of the Gmail inbox closes that person's email on the next sync
- **A12** Enter on a focused Cancel button confirms the dialog: a keyboard Cancel books and charges a courier
- **A13** Bulk Undo on more than 150 emails puts back only the last 150 and says 'Put back'

**Overall.** The one-writer store layer, the Shopify request layer and the booking paths held up under direct attack: corrupt, truncated and NaN files poison and pause as designed, no lost update was found across awaits, and the retry rules for Shopify writes are pinned by tests. What recurs is not missing checks but checks that stop one step short: an ambiguous answer read as a definite one, a failed read treated as a current one, a rule kept in two places that drifted, and page state that a late answer can overwrite. Section 5 groups them.

## 2. Findings in full

### A1 (P2). Saving the Team tab picker for an account on the default tabs grants it Xero sync (fixed 2026-09-22)

`static/index.html:22847` | Team page | mirrored-rule-drift | confirmed-by-running | working ref `M3`

**What goes wrong.** The page's copy of the opt-in tabs is ['recon', 'forecast'], while the server's is ('recon', 'connector', 'forecast'), and the picker's name map has no entry for connector. For an account with no tab list of its own, the picker ticks a box labelled 'undefined' (connector), and any save of that panel sends connector with the rest.

**Reproduction.** Team, People, Tabs on an account that has never had its tabs set. Untick any one tab and press Save.

**Expected.** The picker shows what the server grants: connector unticked and named 'Xero sync', handed over only when ticked on purpose.

**Actual.** The save sends connector and the server stores it. The account can then open Xero sync; an admin on defaults gains Send to Xero and Auto Run.

**Root cause.** b52fbe8 added connector to the server's OPT_IN_TABS and TAB_KEYS; the page's OPT_IN_TABS and the picker's NAMES were not updated. Two copies of one rule.

**Affected.** Any account whose tabs are edited after being on the defaults. The house rule is that the connector, which writes to the books, is handed over deliberately.

**Evidence.** Run in the rig, in a real browser: the picker for a part-time account on defaults listed connector=ON with the label "undefined"; unticking Memory and pressing Save sent {"op":"tabs",...,"tabs":[...,"skills","chat","connector"]}; the account's stored tabs then included connector, and /api/connector answered 200 where it had answered 403.

**Checked against.** Checked the server side of the tabs op: it stores what it is sent, filtered only to known keys, so the page decides. Checked for any other place the page reads the opt-in list: only the picker default. Found by the main session.

**Fix.** Serve the opt-in list and the tab names from the server (the auth state already carries tabs), or at least add connector to the page's OPT_IN_TABS and NAMES.

**Regression test.** A frontend test that the page's OPT_IN_TABS and the picker's NAMES cover exactly the server's OPT_IN_TABS and TAB_KEYS (read copilot.py), so the two cannot drift again. *Existing tests:* No test covers it.

### A2 (P2). Undo on the print toast of a made order's reprint tags it Unprocessed, and Ready to make then puts the made order back into To make (fixed 2026-09-22)

`copilot.py:18111` | Shopify, dispatch and Files | wrong-state-transition | confirmed-by-running | working ref `commerce-02`

**What goes wrong.** B15 made a reprint of a made order not a release (_release_tags returns released=False). But every print, reprints included, gets an Undo toast, and op 'unprinted' calls _sync_order_tags(add=[Unprocessed], remove=[IP]) with no 'unless' guard and clears printed_at. A made order tagged PC becomes 'PC, Unprocessed' and shows in the Unprocessed queue; its 'Ready to make' button (/api/production-labels/queue, also unguarded) then adds IP, putting it back in To make beside PC and re-running the Net-30 attach.

**Reproduction.** A made order waiting in To ship has a damaged label; the operator reprints it, notices the wrong stock was loaded and presses Undo on the toast. The order appears in Unprocessed; someone presses Ready to make; it is now in To make as well as To ship.

**Expected.** Undoing a print that was not a release does not touch tags (or never adds Unprocessed to an order carrying PC/Complete), and the release-queue route refuses or no-ops on an order already made or shipped, as _release_tags does.

**Actual.** before: tags='PC' printed_at set; after reprint: tags='PC'; after Undo: tags='PC, Unprocessed' and printed_at erased; after Ready: tags='PC, IP'.

**Root cause.** The B15 fix put the made/shipped check in _release_tags only; the inverse move (unprinted, 18111-18134) and the other release door (labels_queue_route, 20952) call _sync_order_tags without unless=(MADE_TAG, DISPATCHED_TAG, ...).

**Affected.** Made orders awaiting a label (To ship). Risk of the gobo being made twice, a made order listed in two queues, a lost print stamp, and a repeated Net-30 attempt.

**Evidence.** p11 output: "after reprint:    tags='PC'" / "after Undo:       tags='PC, Unprocessed' state={'made_at': ...}" / "after Ready:      tags='PC, IP'".

**Checked against.** Checked the page: undoPrintBar(ids) is shown after every stampPrinted, with no distinction for reprints (index.html:12648-12680). Checked _sync_order_tags dead-order skip (only cancelled/refunded/fulfilled; a made-unshipped order is live). Checked t_unprint_undoes_a_print: it uses the ORDER fixture tagged 'IP, PC' and asserts Unprocessed is added, i.e. the existing test exercises this path without noticing PC. Re-run by the main session on 2026-09-22: same output.

**Fix.** In op 'unprinted' pass unless=(MADE_TAG, DISPATCHED_TAG, *LEGACY_DISPATCHED_TAGS) and skip orders with a made_at stamp or fulfilled dispatch record (keep their printed_at); give labels_queue_route the same unless guard as _release_tags.

**Regression test.** t_undoing_a_reprint_of_a_made_order_leaves_its_tags: made order tagged PC -> printed -> unprinted -> tags still 'PC'; and /api/production-labels/queue on a PC order does not add IP. *Existing tests:* t_unprint_undoes_a_print should have caught it: its fixture order already carries PC, and it asserts the Unprocessed tag is added.

### A3 (P2). Reconciliation never looks at a finance-mailbox thread again once walked: a new invoice or remittance on that conversation is never read (fixed 2026-09-22)

`recon.py:1235` | Mail, CRM and finance | stale-cache | confirmed-by-running | working ref `mailfin-02`

**What goes wrong.** find_doc_candidates fetches only thread ids not in store['seen_threads'], and the sweep adds every thread it walked to that set, capped at 4000. Documents are keyed per message:attachment, but the thread-level skip means a message added later to a walked thread is never fetched. Two common cases: a supplier replying on last month's thread with this month's invoice, and Gmail threading identical 'Invoice from X' subjects. The new PDF is never read, so a bill missing from Xero is never reported.

**Reproduction.** Sweep 1 reads thread t1, which holds SI-1001.pdf. A month later the supplier replies on the same conversation with SI-1002.pdf. Sweep 2 fetches no threads and reads nothing. SI-1002 is never checked against Xero.

**Expected.** A thread is re-walked when it has changed since it was seen (its historyId, message count or last message id differs). The per-attachment 'known' set already prevents re-reading old documents.

**Actual.** sweep 1: threads fetched ['t1'] | attachments read ['m1'] | seen_threads ['t1']
sweep 2: threads fetched [] | attachments read []
missing-from-Xero findings: ['Supplier Invoice SI-1001 found in Gmail but not in Xero']  (SI-1002 never considered)

**Root cause.** 'Seen' is recorded per thread with no version, so it only means 'had no unread documents when last walked'. The SEEN_CAP comment ('a thread is only ever skipped when its documents were already read') holds only at walk time.

**Affected.** Every supplier invoice, statement or remittance that arrives as a reply on, or is threaded into, an existing accounts-mailbox conversation. The reconciliation's document check reports a clean result for them.

**Evidence.** Ran p8_new_pdf_on_seen_thread.py through recon.sweep() with the suite's _mail_world fakes: output above. Code: recon.py:1235 `fresh = [i for i in ids if i not in seen_threads]`; recon.py:1767 `store["seen_threads"] = sorted((seen | walked) - queued - failed)[-SEEN_CAP:]`.

**Checked against.** Looked for a re-walk trigger (historyId, message count, newer_than on the per-thread fetch): there is none, and list_thread_ids returns bare ids. The tests around seen_threads (13570-13654) cover persistence across reloads and retry after a failed fetch, never a thread that gains a message. git show 9f3b809 records the seen set as a budget optimisation, not a decision to ignore later messages. Re-run by the main session on 2026-09-22: same output.

**Fix.** Store seen as {thread_id: historyId} using list_threads, which already returns historyId, and re-walk when the id differs. Or key 'seen' by last message id. The per-attachment known set keeps the re-walk cheap.

**Regression test.** Two sweeps over one thread. Between them, append a message with a new PDF. Assert the second sweep fetches the thread, reads only the new attachment, and raises gmail_doc_missing_from_xero for it. *Existing tests:* No existing test mutates a thread between sweeps. t_a_document_that_could_not_be_read_comes_back_next_sweep covers only fetch failures.

### A4 (P2). A scanned invoice read on a night the AI call fails is stored as 'ignored' and its thread marked seen, so it is never read again (fixed 2026-09-22)

`recon.py:1374` | Mail, CRM and finance | integration-failure | confirmed-by-running | working ref `mailfin-03`

**What goes wrong.** extract_doc turns any failure of _ai_extract into a stored document {doc_type: 'other', ignored: True, note: 'extraction failed'}. Causes include the daily spend cap (RuntimeError from _spend_guard), an Anthropic outage or overload, and a timeout. Because extract_doc returned a dict rather than None, the sweep stores it under its source_key and marks the thread seen. The next sweep neither re-reads the attachment (it is in 'known') nor re-walks the thread. The same permanent drop happens with no AI configured: adding a key later never re-reads those scans.

**Reproduction.** The daily AI cap is reached during a busy chat day. That night's sweep meets a scanned supplier invoice SI-88812. The next night, with the AI working, nothing is re-read and the invoice's absence from Xero is never reported.

**Expected.** A transient extraction failure leaves the document unread, as a failed Gmail fetch already does (extract_doc returns None, the thread goes in 'failed', and the note says it will be retried).

**Actual.** night 1 (AI unavailable): doc stored as {'doc_type': 'other', 'ignored': True, 'note': 'extraction failed'}
night 1 seen_threads: ['t1'] | notes mention a retry? False
night 2 (AI working): AI calls made = 0
night 2: 'found in Gmail but not in Xero' raised for SI-88812? False
control (AI working on the first night): raised = ['Supplier Invoice SI-88812 found in Gmail but not in Xero']

**Root cause.** extract_doc conflates 'this document is not a financial document' (ignored) with 'we could not read it' (retry). The sweep's retry path keys only on a None return.

**Affected.** Scanned supplier invoices, credit notes and remittances (the documents that need the AI) arriving on any day the AI is capped, down or unconfigured. They drop out of the reconciliation permanently and silently.

**Evidence.** Ran p7_scan_dropped_on_ai_failure.py through recon.sweep() with _mail_world, an ai_call raising the real spend-cap message, then a working ai_call: output above. Code: recon.py:1371-1374 returns the ignored dict when _ai_extract returns None; _ai_extract (1449-1469) catches every exception and returns None; recon.py:1756-1767 stores any truthy result and marks the thread seen.

**Checked against.** Searched recon.py, copilot.py and the tests for anything that re-reads 'extraction failed' or 'scanned document and no AI configured' documents: none. The sweep comment 'Extraction failed: the document is NOT read, so its thread must come back' shows the intended rule, applied only when extract_doc returns None. Re-run by the main session on 2026-09-22: same output.

**Fix.** Have extract_doc return None, not an ignored stub, when the AI call raises or returns no tool block, and when no AI is configured, so the thread stays out of seen_threads and the note says it will be retried. Keep 'ignored' for real non-documents and duplicates.

**Regression test.** Sweep with ai_call raising RuntimeError, then with a working ai_call. Assert the second sweep reads the attachment and raises gmail_doc_missing_from_xero. Also assert the first sweep's notes mention a retry. *Existing tests:* _mail_world configures ai_call=None and no test drives a failing AI call through a sweep, so the stub path was never asserted against the retry rule.

### A5 (P2). When Xero cannot be read, the sweep checks new Shopify orders against the Xero copy cached by the last good sweep and reports each as a sale missing from Xero (fixed 2026-09-22)

`recon.py:1787` | Mail, CRM and finance | stale-cache | confirmed-by-running | working ref `mailfin-04`

**What goes wrong.** A failed Xero fetch (a dead grant, a Xero outage, or a 429 that outlasts the capped retries) only appends a note. The 'failed read is not an empty ledger' gate skips the sale, refund and payout checks only when the cached invoices are EMPTY. With yesterday's cache present, every order placed since the last good read is raised as shopify_sale_missing at high, or critical over £250, although its invoice is in Xero. The same applies to payouts and refunds after the last good read. With a dead grant (invalid_grant) this repeats every night, and the board fills with false highs until someone reconnects.

**Reproduction.** Night 1 sweeps normally. The Xero grant then dies, or Xero is down at sweep time. Orders #104301 (£95) and #104302 (£480) are placed and their invoices reach Xero. Night 2's sweep cannot read Xero and reports both as missing from Xero.

**Expected.** When a Xero bucket could not be read this sweep, the checks that depend on it are skipped, and their old findings kept but not staled, as already happens for the empty cache and for a short Shopify read (orders_short).

**Actual.** night 2: open {'critical': 1, 'high': 1, 'medium': 0, 'low': 0}
  EXCEPTION high shopify_sale_missing - Shopify sale #104301 (£95.00) has no matching Xero invoice
  EXCEPTION critical shopify_sale_missing - Shopify sale #104302 (£480.00) has no matching Xero invoice
(notes only say 'Xero invoices could not be read: ...')

**Root cause.** xero_has_data = bool(cache['xero']['invoices']) tests whether a cache exists, not whether this sweep refreshed it. The per-bucket fetch failure is not carried to the check selection.

**Affected.** Reconciliation users after any Xero read failure, and every night while the Xero grant is dead: false high and critical sale, refund and payout discrepancies that bury real ones.

**Evidence.** Ran p3_dead_xero_grant_stale_books.py through recon.sweep() with _recon_world/_FakeXero, then a fake whose four list_* calls raise the real invalid_grant message: output above. Code: recon.py:1646-1648 appends a note and continues; recon.py:1787-1793 gates only on an empty invoices cache.

**Checked against.** Checked git show 1dd2d59, where the gate was introduced for the empty-cache case only. Checked that the xero_api.connected() gate in _recon_nightly and the sweep route passes with a dead grant (the token file still exists). Checked B32 (disconnect clears the cache), which does not apply because a dead grant is not a disconnect. No test drives a failed read with a warm cache. Re-run by the main session on 2026-09-22: same output.

**Fix.** Track which Xero buckets failed this sweep. If invoices failed, skip check_orders_vs_invoices and check_xero_orphan_sales. If credit_notes or bank failed, skip check_refunds, check_disputes and check_payouts_vs_bank. ## 4. Test-suite gap analysis

The suites pass (785 dispatch, 341 page, 17 forecast), and they are strong where a bug was once found and pinned. The gaps are where tests use data shapes or failure modes that are kinder than real life.

- **Unhappy paths that cost money run only against writers that always succeed.** No test drives a 5xx through the real World Options transport on DoShipment (A9), a relayed 504 (A22), or a lost answer on orderUpdate, fulfilment or Net-30 when the settling re-read also fails (A23, A26). *Missing integration tests*, one per writer: answer lost, re-read fails, what does the page say.
- **Fixtures are cleaner than real data.** The attachment test builds parts with no headers at all, so a filter that drops every Gmail and Apple Mail attachment passes (A10). *Add fixtures captured from real (redacted) Gmail part trees* for the three common clients.
- **Failure with previous state is the untested case.** Reconciliation tests fail the Xero read only when the cache is empty (A5); the Customers tab has no failed-read test (A27); the finance-mailbox tests never add a message to a walked thread (A3). *Regression tests for "the read failed and yesterday's copy exists".*
- **Some tests pin the bug.** `t_webhook_registration_is_a_standing_repair` asserts refunds/create is registered at an endpoint that refuses it (A20); `t_unprint_undoes_a_print` runs A2's exact path with a made order and asserts only that Unprocessed was added. *These tests are too implementation-specific*: assert the outcome (the delivery is accepted; a made order stays made).
- **Guards that scan one file or one spelling.** The no-native-dialog guard reads only index.html (A47) and the dash guard looks for the literal character, not the escape `\u2014` (A48). *Extend both to composer.js and to escapes.*
- **Rules kept in two places have no parity test.** The page's opt-in tabs drifted from the server's (A1). *A test that reads copilot.py and compares every constant the page mirrors.*
- **Page behaviour is tested for a few flows only.** The node harness pattern (real functions, held api()) is proven; it covers the recon list, the loan picker and the chat stream. Missing: every in-flight guard (A31, A33, A34, A35), keyboard answers to dialogs (A12), bulk undo over the chunk size (A13), drafts across a tab switch (A36).
- **Runtime properties with no test:** `_json_cache` stays bounded (A41), the backup does not block the event loop (A42), a malformed numeric environment value (A25), the log drain's real sender (A24), redaction with deals, leads and enquiry threads and with a failed write (A7, A14).
- **CI never runs `tests/test_forecast.py`**, and bandit's file list omits `forecast/`. The nightly service can break without CI noticing.

## 5. Architecture-level findings

Six recurring classes; a fix to the class closes several rows.

1. **An ambiguous outcome still read as a definite one** (A9, A22, A23, A26, A32; and inversely A24, where a refusal reads as success). The 2026-09-19 pattern 4 was fixed where it was found; it lives on at the transport edges: HTTP 5xx pages, relayed timeouts, rejected fetches and lost answers whose re-read also failed. One rule for every write: unknown is its own state, the page says "may have gone through, check before retrying", and nothing re-arms.
2. **A failed or partial read treated as the current truth** (A5, A27, A16, A15, A4, A3). The app's own rule for mirrored state (promotion is free, demotion needs proof) is applied to Gmail's unread flags and not to Xero's books, Shopify's customers or the finance mailbox. Carry a read's completeness with its data and refuse to conclude from a read that was not whole.
3. **One rule kept in two places, drifting** (A1, A17, A46, A44, A47, A48). The house lesson from the collections bug ("two code paths computing the same key must call one function") applies to the page-server boundary too: opt-in tabs, crown postcodes, London times, what the customer paid for delivery.
4. **Records and restore points that come after the irreversible act, or can be overwritten** (A21, A8, A14). The booking is recorded after the label download, not first as the architecture document says; the pre-import snapshot shares a name with any later one that day; a redact that could not be written is logged as done.
5. **Page state without in-flight guards or sequence numbers** (A13, A31, A33, A34, A35, A36, A39). cba9d24 gave the recon list and the loan picker sequences; the pattern is not yet general. One helper (a per-view sequence, a per-control in-flight flag) would cover them.
6. **Per-item memory with no bound** (A41, A40). A cache written for every path, and a fetch read whole before it is cut.

Not assessed this session: missing authorisation checks and the AI boundary (see the executive summary).

## 8. Method

Five area finders ran in one workflow within the five-agent cap: persistence and runtime; Shopify, dispatch and Files; mail, CRM and finance; the page; access and identity. Each was briefed with the bug definition, what the 2026-09-19 audit and the security passes already closed or accepted, the house rules that count as requirements, and a harness that builds the test suite's helpers without running it. Each finding needed a proof script and a refutation attempt. The main session re-ran every proof script, read the cited code for the rest, ran the browser pass, reviewed the deployment, CI and extensions, and wrote this register. Nothing was sent to a live Shopify, Gmail, Xero, World Options or any other outside service; the rig refused all outside traffic.

## 9. What was fixed

All 48 findings were fixed on 2026-09-22: the thirteen P2s first, then the thirty-five P3s, each set when Cameron asked for it. Every fix carries a test, and every one of those tests was run against the sources as audited (`cba9d24`) and fails there. The page's fixes are tested by running the real functions in node where the fault is behaviour (a second paid run, a late plan, two windows, a repaint under typing, a reload on a signed-out boot) and by reading where it is a rule. An independent reviewer read the P2 diff three times and the P3 diff once, and every gap it proved was closed before the commit. Its P3 pass found six, each now with a test that fails without its fix:

- A World Options FAILED reply relaying "(504) Gateway Timeout" was no longer re-sent (A22), but the booking path still read it as a refusal: the guard was cleared and Book re-armed, so a second press booked and charged again. It is now the same unknown outcome as a lost answer.
- An address changed in the Shopify admin never passes the app's edit route, so Mark made still emailed tracking for the old address (A26). Mark made now reads the order and compares it with the address the label was cut for.
- Customers kept one in-flight sector for the whole tab, so running a second sector and going back ran the first again (A31). It now keeps one run per sector.
- A made order Shopify no longer has (a deleted test order) held that day's stock sheet for good as "could not be read just now" (A16). It is left out of the sheet, its own booking stands, and the send says which; an order that could not be read is named in the refusal.
- Net-30's one caller put "could not be added" in front of "it is not known" (A23). An unknown outcome is now worded as unknown.
- Coming back to the Products tab painted the list and let a running plan land over it (A33). Any route to the list now drops the plan, and a tab switch mid-run keeps the plan's loading screen.

It also found that three tests passed with their fix undone (A14's hourly hook, A23's no-revert guard, A44's booking record) and four page tests only read the source (A34, A36, A37); those now drive the real code. Smaller items it raised and that were closed: a retried erasure no longer moves the recorded request time, a capped missing-from-production check says so even when it finds nothing, and the erased-address patterns no longer evict each other.

What changes for the people using it:

- **A1 does not take back what the bug gave.** An account handed Xero sync by a save of the Team tab picker keeps it. Open Team, People, Tabs for each account and untick Xero sync wherever it was not meant.
- **A21 can hold Book.** A booking whose answer never came back (a deploy or crash mid-booking, or a lost reply) now stops the next Book on that shipment with "A booking may already exist". Check World Options for a new shipment first; only then press "I checked: book it". The hold lapses after 48 hours.
- **A9, A22, A23, A26, A32: "may have gone through" is its own answer.** A booking, a fulfilment, a Net-30 write, an address edit or an email whose answer was lost is settled by reading it back where that is possible, and otherwise said to be unknown, with no button re-armed to do it a second time.
- **A25:** a numeric setting that is not a number now falls back to its default and logs a warning naming it, rather than stopping the app. After changing one in Railway, look for that warning.
- **A18:** shifts beyond the newest 2,000 move to `worklog_archive.jsonl` beside the log (`WORK_ARCHIVE_PATH`), and the payroll report still reads them.
- **A20:** the next hourly webhook pass deletes the refunds/create subscription the endpoint always refused.
