# Bug audit, 2026-09-19

A whole-app hunt for real bugs: behaviour a person or the business would meet that is wrong, as distinct from missing controls (the security registers) or structure (the architecture audit). Scope: copilot.py, server.py, the root integration modules, static/index.html and composer.js, forecast/, and the tests. The Node connector service is a separate repository and was not read.

**Written in report mode.** Every finding is a description of the code as it was on `5f60daa`, with a one-line fix sketch; which to fix, and in what order, was Cameron's decision, and the section after the headline records what he chose and what was then closed.

## Headline

48 findings: 0 critical, 7 high, 25 medium, 16 low. Baseline before the audit: `make check` green (740 dispatch tests, the frontend guards, the tree sweep, the environment reference).

Every finding was verified in the main session by re-reading the cited lines with the callers and guards around them, not taken on the finder's word. 27 of them were also reproduced by running a script against the real functions (the finders' scripts, re-run from scratch here); the rest are unambiguous on reading. Confidence is stated per finding.

Five patterns account for most of the list; a fix that addresses the pattern closes several rows at once.

1. **A memory copy that outlives the file.** The mailbox and Files caches survive shop/redact and put the erased data back within a minute (B2); restore forgets the loans cache (B9); a Pipedrive preview edits the live cached CRM (B6); a sweep's tail rewrites a disconnected Xero cache (B32). One cause, four rows: a hand-rolled `_mem` or a shared cached object that nobody drops when the disk changes underneath it.
2. **UTC where the business runs on London time.** The payroll CSV (B10), the label's Required-by urgency (B35), the Forecast chart's Today and This month ranges (B22), the forecast's month buckets (B47). The dispatch code already does this right with `ZoneInfo("Europe/London")`; these four did not follow it.
3. **First match wins, and nothing is claimed.** In the reconciliation one credit note explains any number of equal refunds (B7), one SPEND line any number of equal chargebacks (B30), an invoice matched by order number is matched again by amount (B28), and an invoice with no contact matches anything of its amount (B48). `check_payouts_vs_bank` has the claimed set the others lack.
4. **An ambiguous failure read as a definite one.** A reply whose Gmail answer times out is recorded as not sent and the retry sends it twice (B5); a proxy 5xx tells the dispatcher 'Nothing was saved' when the booking may have gone through (B21).
5. **Shopify's original quantity, not its current one.** A refunded or edited-out line still prints, still books glass, still counts in the declared value (B4). One helper would close it everywhere.

The two highs outside those patterns: the boot re-seal of MFA secrets has never sealed anything because it reads the wrong file shape (B3, and the test that hides it, B34), and the Shopify outage flag is never cleared, so one three-hour outage means a 'recovered' email every hour and scheduled audits skipped three ticks in four, indefinitely (B1).

## Fixed on 2026-09-19

Cameron asked for the seven highs and the pattern fixes. Eighteen rows were closed in the commit that follows this register, each with a test that fails on the code as audited and passes on the fix: the highs B1 to B7 (and B34, the test that hid B3); the cache pattern B2, B6, B9, B32 through one registry of memory copies (`_memory_stores`) that restore and shop/redact both drop; the London-time pattern B10, B22, B35, B47 through `_london_today`, `_london_day`, a London `_day_starts` and a local-day `fcISO` (and the loan register's due date, found by review); the claimed-set pattern B7, B28, B30, B48 in recon.py, where refunds and chargebacks are now ASSIGNED to records by a maximum matching rather than first-come, because an independent review showed a claimed set alone flags a refund whenever the first refund takes the one record the second needed; the ambiguous-failure pattern B5 and B21, with the sync now settling a lost-answer stamp when it finds the shop's own message in Gmail, and the page showing a send warning it used to drop; and the quantity pattern B4 through `_line_qty`. Two judgment calls, said plainly: shop/redact now drops the two Gmail grants (the sync would otherwise rebuild the erased mailbox from Gmail within a minute; reconnecting is one sign-in) but keeps Xero and the courier credentials (neither holds the shop's data, and the courier key is typed in with nowhere to get it back from after a misfire); and a reply Gmail files onto another conversation is recorded as SENT with a warning rather than refused, because the customer has the email either way. Left open from the review, on purpose: the margin report still counts a refunded unit's revenue and cost (beside B13, which it shares a fix with). The rows below marked fixed are kept as written, as the record of what was found.

## High

### B1. Watchdog never clears the Shopify outage flag: hourly 'recovered' emails and 3 of 4 scheduler ticks skip audits forever (fixed 2026-09-19)

`copilot.py:8925` | Core, auth, stores | wrong-state | confirmed-by-running

**What the code does.** _watchdog_tick pops shopify_down from its in-memory `state` when the probe succeeds, but then persists with `fresh = _load_watch(); fresh.update(state)`. A key absent from `state` is not removed from `fresh`, so shopify_down written to disk during the outage is never deleted. Every later hourly tick sees it set, sends the 'connection recovered' email again, and the 15-minute early-return path reports Shopify as down.

**How it shows.** Shopify token rotated or a Shopify outage lasts 3 hours; the app flags the outage (correct). Shopify comes back. From then on: an email 'Reactor: Shopify connection recovered' every hour indefinitely; between hourly probes _watchdog_tick returns not shopify_down == False so _scheduler_loop logs 'Shopify unreachable; skipping paid audits' on three of every four ticks (scheduled audits only get a chance on the hourly tick); Settings > Connections shows down_since permanently.

**Evidence.** copilot.py:8838-8839 `if up and state.get("shopify_down"): state.pop("shopify_down", None)`; copilot.py:8923-8926 `fresh = _load_watch(); fresh.update(state); _save_watch(fresh)`; copilot.py:8820 `return not _load_watch().get("shopify_down")`; copilot.py:22165 `"down_since": watch.get("shopify_down")`. Ran with a mocked probe: after 3 failures then recovery, shopify_down was still on disk after each of 3 'up' ticks, the recovered email was sent on every one, and the intermediate tick returned shopify_up=False.

**Checked against.** The merge was added deliberately (comment at 8918-8922) to stop team_established being erased, so it is not a slip that some other code compensates for: nothing else ever pops shopify_down (grep shows the only writers are this tick). No test covers the recovery path (grep shopify_down in tests returned nothing).

**Fix sketch.** Track removed keys explicitly: on recovery do `fresh.pop("shopify_down", None)` after the merge (or write a tombstone list of keys the tick deleted and pop them from `fresh`).

### B3. Boot re-seal of MFA secrets is a no-op: reseal_users reads the wrong file shape (fixed 2026-09-19)

`tokenvault.py:175` | Core, auth, stores | auth | confirmed-by-running

**What the code does.** users.json is written by _write_users as {"users_store": {"version": 2, "users": {...}}} but tokenvault.reseal_users does data.get("users") on the top-level object, which is always None, so it returns 0 and never seals anything. **How it shows.** Cameron enrols TOTP, later sets TOKEN_ENCRYPTION_KEY and redeploys. Ran: with a key set, reseal_secrets_at_rest() returned {'sealed': 0, 'stores': {... 'mfa': 0}} and the secret on disk was still 'PLAINSECRET'; token_vault_state() reported plaintext: ['A sign-in code secret'].

**Checked against.** Checked whether the mfa routes seal at write time (they do: copilot.py:18926/18940 use tokenvault.seal), so only pre-key enrolments are affected, which is exactly the case reseal exists for. Checked token_vault_state (copilot.py:12063) which correctly unwraps users_store, so the Settings panel would show the plaintext count, but nothing acts on it. The only test (tests/test_dispatch.py:17324) writes the unwrapped shape and therefore passes.

**Fix sketch.** In reseal_users, unwrap `data = data.get("users_store", data)` before reading users (or pass the store key in), and change the test fixture to the real on-disk shape.

### B4. Refunded or removed line items still print, consume glass and inflate the declared value (fixed 2026-09-19)

### B5. A reply whose Gmail answer times out is recorded as 'did not send', so the retry sends it twice (fixed 2026-09-19)

`copilot.py:16176` | Inbox, Files, WebDAV | double-send | confirmed-by-running

**What the code does.** The reply path catches every exception from google_mail.send_message in one branch, pops the durable send_pending stamp, logs 'the send did not complete' and returns 502 'Gmail would not send this reply.' That is right for a GmailError (Google refused), but an httpx.ReadTimeout/ConnectError after the upload POST left the machine means Google may well have accepted and delivered the message. The stamp that exists precisely for 'we do not know' is removed and the person is told nothing went. The same branch also swallows google_mail's own 'The reply was sent but Gmail could not attach it to this conversation' GmailError, which by its own wording is a delivered email, and leaves no sent_at, no state change and no stamp.

**How it shows.** Staff member replies with a 20MB artwork attachment; the 120s upload completes at Google but the response is lost (read timeout). Board shows 'the send did not complete: Gmail would not send this reply.' with the Send button re-enabled (index.html mailSendFlow re-enables on error). They press Send again; the customer receives the reply twice, the thread records only one send, and the hourly cap counts both.

**Evidence.** copilot.py:16167-16182: `except Exception as e:\n reason = (str(e) if isinstance(e, google_mail.GmailError) else "Gmail would not send this reply.")\n ... # The stamp is there to outlive a CRASH. This is not one: we know how it ended, so it comes off\n t.pop("send_pending", None)\n _mail_log(t, who, "the send did not complete", reason)`. google_mail.py:_upload_post uses httpx with timeout=120 and lets ReadTimeout propagate. Ran proof.py: first send raised httpx.ReadTimeout after the fake delivered -> 502 {'error': 'Gmail would not send this reply.'}, send_pending None in memory and on disk; second send -> 200; delivered list had 2 entries for jo@customer.com. Variant with GmailError('The reply was sent but...') -> send_pending None, sent_at None, state unassigned.

**Checked against.** Looked for a timeout-specific branch or an isinstance check on httpx.TimeoutException/TransportError: none in the route or in google_mail.send_message/_upload_call. The test t_a_failed_send_marks_nothing_sent_and_leaves_no_stamp only covers GmailError, so it does not pin the timeout case. The page's mailSendFlow re-enables Send now on any error, so the retry is one click. The new-message path (16277-16283) has the identical shape with _mail_outbound_drop.

**Fix sketch.** Only clear the stamp on a definite refusal (GmailError raised before the upload was accepted, i.e. a 4xx/5xx answer); on httpx.TimeoutException/TransportError, and on the 'was sent but landed elsewhere' GmailError, keep send_pending and answer 'may have gone out, check Sent before sending again'.

### B6. A dry-run Pipedrive import mutates the live CRM cache; a partial export strips contacts off deals (fixed 2026-09-19)

`copilot.py:17648` | Reconciliation, CRM, analytics | data-loss | confirmed-by-running

### B7. Two refunds of the same amount both 'match' one credit note, hiding the unrecorded one (fixed 2026-09-19)

`recon.py:474` | Reconciliation, CRM, analytics | wrong-money | confirmed-by-running

**What the code does.** check_refunds has no claimed set: every refund independently scans all credit notes and SPEND lines and takes the first same-amount record within 10 days, so one credit note in Xero satisfies any number of equal-amount Shopify refunds. check_payouts_vs_bank claims its bank lines precisely to avoid this; refunds do not.

## Method

Finders were briefed with what counts as a bug (crashes on inputs that can arrive; wrong money, weight, date or quantity arithmetic; data loss and races; wrong state transitions; double actions; wrong auth outcomes; injection with a reachable path; swallowed failures; silent truncation; wrong or stale output on the page; tests that pin a bug) and what does not (style, refactors, speculation, decisions recorded as deliberate in docs/, and the items already open in the 2026-09-07 security audit). Each finding had to cite the defective line, give a concrete scenario, quote its evidence, and record the attempt to refute it. Severity: critical = money, data or security wrong on the normal path; high = wrong on a common path or one ordinary precondition away; medium = an uncommon but real path, or wrong information on screen; low = cosmetic, or a test pinning a bug.

The finders' proof scripts and this register's source data are in the session scratchpad (`audit/`); the register is the durable record.
